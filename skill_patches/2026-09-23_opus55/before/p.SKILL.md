# プライベートリスト ランナー（/p）

`/p` は `/t` と同じ使い方。**番号を打ったらそのタスクを実行する。**
違いは対象が マイタスク の **プライベートリスト（`list_id: private`）** に限られること。

- `/p 296` / `/p296` / `/p MYT-0296` → MYT-0296 を実行（確認を挟まずそのまま作業に入る）
- `/p 296 293` → 296 → 293 の順に1件ずつ実行
- `/p`（番号なし）→ プライベートの未完了一覧を出し、番号を選んでもらう
- `/p 296 見せて` → 中身を見せるだけで実行しない

`MYT-` の有無、ゼロ埋めの有無は問わない（`296` = `0296` = `MYT-0296`）。

## 使うツール

マイタスク MCP サーバーのツールを使う（ブラウザ操作は不要）。
必要なら `ToolSearch` で以下を読み込む:

```
select:mcp__34d5bb3f-82d5-4fc0-9e0d-6699c55b1caf__list_tasks,mcp__34d5bb3f-82d5-4fc0-9e0d-6699c55b1caf__get_task,mcp__34d5bb3f-82d5-4fc0-9e0d-6699c55b1caf__update_task,mcp__34d5bb3f-82d5-4fc0-9e0d-6699c55b1caf__complete_task
```

サーバー ID はセッションによって変わることがある。上記名で見つからなければ
`ToolSearch` に `mytasks task list` 等のキーワードを渡して同等のツール
（`list_tasks` / `get_task` / `update_task` / `complete_task`）を探す。
`mytasks.yonetani32ai.workers.dev` に `curl` / `WebFetch` で直接叩かない（401/403 になる）。

## Step 1 — 番号を確定する

**番号が付いている場合**（主動線）: `get_task(ref="MYT-0296")` で1件取る。
そのタスクの `list_id` が `private` でなければ、実行せずにその事実を伝えて指示を仰ぐ
（`/p` はプライベート用のコマンドなので、仕事リストのタスクは `/t` に回す）。
番号が存在しなければ、近い番号を推測せず「無い」と伝える。

**番号が付いていない場合**: 一覧を出す。

```
list_tasks(list="private", status="open", full_note=true, limit=50)
```

番号・タイトル・期限・`risk_level`・情報の充足状況を1行で並べる:

```
MYT-0296  冷蔵庫の保証書を探してドアの緩みをヤマデンに修理依頼   期限なし / B / 情報不足
MYT-0294  掃除ロボットの汚水タンクを空にする                     期限なし / B / 情報不足
```

そのうえで「どの番号をやりますか」と聞き、番号が返ってきたら Step 2 へ。
「一覧だけ見たい」場合はここで止める。

## セッション名（強制・/t と同じ）

番号が確定したら最初のツール呼び出しの直後に `mcp__ccd_session_mgmt__set_session_title`（`session_id="self"`）でセッション名を `T-<番号> <着手日YYMMDD> <タイトル要約>` へ変更する（例：`T-295 260825 シャワーヘッド後継品の適合確認`）。`Page 295`・`Grilling page 295` など自動命名のまま作業を続けない。番号なし起動（一覧表示）のときは番号が決まった時点で変更する。セッション名変更ツールが無い環境（Cowork・claude.ai・Codexアプリ等）ではスキップしてよい。

## Step 2 — 実行する

`get_task` の全項目と `readiness` を見て作業に入る。

**note が空、または `readiness.missing` があっても止まらない。**
ただし計画・決断・仕組みづくり系のタスクだけは、下の「詰めラウンド（grilling 内蔵）」を先に回してから下準備へ進む。買い物・修理依頼・物理作業のような定型タスクは従来どおり止まらずに進める。
タイトルから対応内容を推測して、AI 側でできる下準備を先に進める。例:

- 型番・保証期間・修理窓口・受付時間・料金相場を調べる
- 依頼メール / 電話で言うことの下書きを作る
- 注文候補（型番・価格・入手先）を比較して1〜2案に絞る
- 予約に必要な情報（診察券番号・希望日時候補）を整理する

推測が外れると手戻りになる要点（どのメーカーか、誰の予約か、予算はいくらか等）
**だけ**をまとめて本人に聞く。全項目の穴埋め質問はしない。

物理作業（タンクを空にする、浄水器を取り付ける）が本体のタスクは、
AI が代行できる部分（手順の確認、必要な部材、注意点、所要時間）を出して、
実行そのものは本人の作業として残す。

### 止める線（automation_priority_roadmap.md の判断ルール）

- 自動送信しない。メール・問い合わせフォーム・予約確定は**下書き止まり**にして、本人が送る
- 自動削除しない
- 注文・支払い・契約は下書き止まり
- `risk_level` が B / C のタスクは、実行の最後の一押しを必ず本人に渡す

## 詰めラウンド（grilling 内蔵）

**発動条件（次のどちらかに当てはまるときだけ。1行で「→ 詰めラウンドに入ります（理由）」と告知してから始める）**

- `readiness.can_start=false` または `readiness.missing` があり、不足が「聞かないと決まらない判断」を含む。
- タスクの中身が**計画・決断・アイデア・仕組みづくり・設計**を含む（何を作るか／どの方式でいくか／どこまでやるかが未確定）。

定型作業（返信・申請・整理・転記・打刻・単純な調べもの）では発動させない。そのまま実行する。
本人が「詰めて」「ストレステストして」と言ったときは条件にかかわらず発動する。

**進め方（正本＝grilling スキル。以下は実行に必要な要点）**

1. 対象を**設計ツリー**として捉え、**フロンティア**（前提となる決定が固まっていて「今」聞ける質問）だけを1ラウンドで一気に聞く。まだ答えの出ていない質問に依存する質問は次ラウンドへ回す。
2. 質問は**選択式**で出す。`AskUserQuestion` で**1ラウンド最大4問**、各問**候補3つ**（「その他」はツールが自動で4番目に付けるので自前で作らない）。**推奨候補を先頭**に置き末尾へ「(推奨)」＋理由・トレードオフを一言。ツールが無い環境では `❓ Q1 …` の番号選択形式テキストで出す。
3. **既存実装の棚卸し（強制）**：実装手段・技術の選択肢を出すラウンドの**前に**必ず ①`find ~ -iname "*<対象名>*"` ②`grep -il "<対象名>" ~/.claude/projects/*/memory/MEMORY.md` ③自動化・常駐・定期実行が絡むなら `ls ~/bin ~/Library/LaunchAgents; launchctl list | grep -v com.apple; crontab -l` を実行する。この確認より前に「未実装」を前提にした選択肢を出さない。Mac実機のシェルに繋がっていない環境（Cowork のVM構成など）では空振りするので、「棚卸しができていない」と明示し、実装手段のラウンドを後ろへ回す。空振りを「既存資産なし」と結論しない。
4. **調べられる事実は自分で調べる**（必要ならサブエージェント）。ユーザーに聞くのは**決定そのもの**だけ。調査待ちでも止まらず、調査結果に依存しない質問は今すぐ聞く。
5. 回答のたびにフロンティアを再計算してラウンドを繰り返す。**フロンティアが空＝暗黙の前提が残っていない状態**になったら実作業へ進む。それ以前に実作業を始めない。
6. **各ラウンドの確定事項は `update_task` で note へ書き戻す**（`対応:` `背景:` `確認事項:` `完了条件:` `期限根拠:` の既存見出しに載せる）。決まったことを会話に置いたまま実作業へ進まない。
7. セッション名はタスク側の規約（`T-<番号> <着手日YYMMDD> <タイトル要約>`）を使う。grilling 単体用の命名規則へ切り替えない。

## Step 3 — 分かったことをタスクに書き戻す

調べた内容や決まったことは `update_task` で `note` に残す。行頭見出しは決まった語を使う:

```
update_task(ref="MYT-0296", note="対応:\n...\n背景:\n...\n確認事項:\n...\n完了条件:\n...\n期限根拠:\n...\n出典:\n...", workflow_state="awaiting_confirmation")
```

- 既存の `note` がある場合は上書き前に内容を読み、消えて困る記述を残す（既存ファイルの上書きは確認後、と同じ扱い）
- 本人の確認待ちで止めたものは `workflow_state="awaiting_confirmation"`
- 作業途中なら `in_progress`

## Step 4 — 報告と完了

1件終わるごとに「やったこと / 残っていること / 本人がやる必要があること」を短く報告する。

完了扱いにするかは**必ず本人に聞く**。勝手に閉じない。
OK が出たら `complete_task(ref="MYT-0296")` を呼ぶ（繰り返し設定があれば次回分が自動生成される）。

複数番号をまとめて指定された場合も、1件ずつ Step 2〜4 を回し、完了確認はタスクごとに取る。
